# Tooling

Cross-file invariants that the canonical config files of a PHP service must satisfy together. The **canonical file
bodies** (the full `composer.json`, `Makefile`, `phpunit.xml`, `phpcs.xml`, `phpstan.neon`, `infection.json.dist`,
`.editorconfig`, `.gitattributes`) are generated by the php-creating-skeleton skill, the single source of truth for
scaffolding a new service or restoring a file. This rule keeps only the invariants that span more than one file and the
audit signals checked against an existing service.

Repository root layout and the `docker/`, `.env`, and Dockerfile assets are owned by `skeleton-layout`.

## Pre-output checklist

1. The repository root contains all of: `composer.json`, `phpunit.xml`, `phpcs.xml`, `phpstan.neon`,
   `infection.json.dist`, `.editorconfig`, `.gitattributes`, `Makefile`. See § Config files.
2. `composer.json` `require.php` is the single source of the PHP `major.minor`. The `Makefile` derives it, and both
   Dockerfile `FROM` lines carry the same literal (the base image tag encodes it, whichever base is in use). See § PHP
   version.
3. Mandatory core dependencies are present. A conditional dependency appears only when its trigger condition holds. Each
   declared `ext-*` matches a direct call in the service's own code. See § Dependencies.
4. `minimum-stability` is `stable`, and every private package has its `repositories` entry. See § Stability and private
   repositories.
5. No canonical library lags a major behind the latest stable without an `@upstream` comment. See § Audit signal.
6. `composer.json` exposes exactly the closed set of six scripts: `configure`, `configure-and-update`, `fix-review`,
   `review`, `test-file`, `tests`. See § Six scripts.
7. `infection.json.dist` sets `minMsi: 100` and `minCoveredMsi: 100`. Lowering either is prohibited. See § Coverage and
   mutation thresholds.
8. All test artifact paths use `reports/` (plural), consistent across `composer tests`, `infection.json.dist`,
   `phpunit.xml`, and the `Makefile`, and each artifact sits in the subdirectory of the tool that writes it. See §
   reports consistency.
9. The `Makefile` carries the closed public target set, declares no target outside it and no prerequisite on any of
   them, declares exactly two container runners, and leaves no unreferenced variable. See § Makefile shape.
10. Every container runner in the `Makefile` that executes `composer` forwards the private-package credential. See §
    Private package authentication.
11. A service that owns a schema removes its migration container as the last line of the `start` recipe, with no error
    tolerance. See § Migration container removal.

## Config files

The config files all live at the repository root. `phpunit.xml`, `phpcs.xml`, and `phpstan.neon` are committed live (the
test configuration and the rulesets are identical in every service, so there is no per-clone override story).
`infection.json.dist` is committed as the `.dist` baseline a contributor may override with a gitignored
`infection.json`. Do not introduce a `.dist` twin for `phpunit.xml`, `phpcs.xml`, or `phpstan.neon`, and do not commit a
live `infection.json`. PHPStan runs at level 5 over `src` and `tests` as the second step of `composer review`. Level 6
is the ceiling that would demand iterable value-type docblocks on concrete classes, which the `php-code-style` PHPDoc
rule prohibits, so raising past 5 requires revisiting that rule first. This platform does not use `psalm`,
`php-cs-fixer`, or `pest`: their absence is deliberate, and none of them is added without an explicit request.

The canonical body of every file above is in the php-creating-skeleton skill.

## PHP version

`composer.json` `require.php` is the single source of the PHP `major.minor`. The `Makefile` derives it into
`PHP_VERSION` and never pins it, so `PHP_IMAGE` follows the declaration on its own. Only
`Dockerfile.dev` and `Dockerfile.prod` still carry a literal `major.minor`, because a Dockerfile cannot read
`composer.json` at parse time. A PHP bump therefore touches exactly two places, `composer.json` `require.php` and both
`FROM` lines, and the two must agree. The `FROM` lines reference the shared base images published under `<base-images>`
(`<base-images>/php:<minor>-development-<V>`, `<base-images>/php:<minor>-builder-<V>`,
`<base-images>/php:<minor>-runtime-<V>`), whose tags encode the PHP `major.minor`, so a PHP bump also requires a base
image release (docker-images rule). With `<base-images>` unset the `FROM` lines reference the upstream official image
and the tag grammar becomes `php:<minor>-cli` and `php:<minor>-fpm`, which encodes the same `major.minor`. No base image
release is involved then, and the invariant is untouched: `require.php`, both `FROM` lines, and the tag all carry one
`major.minor` and must agree.

## Dependencies

Mandatory core libraries (every service is born with exactly these, the last row only where `<auth-package>` is set):

| Concern          | Library                            |
|:-----------------|:-----------------------------------|
| HTTP framework   | `php-di/slim-bridge`               |
| HTTP messages    | `slim/psr7`                        |
| HTTP helpers     | `tiny-blocks/http`                 |
| Validation       | `respect/validation`               |
| In-house core    | `tiny-blocks/building-blocks`      |
| Environment vars | `tiny-blocks/environment-variable` |
| Error handling   | `tiny-blocks/http-error-handler`   |
| Health checks    | `tiny-blocks/http-health-check`    |
| Request logging  | `tiny-blocks/http-logging`         |
| Logger           | `tiny-blocks/logger`               |
| Auth middleware  | `<auth-package>`                   |

The last six are mandatory because the canonical `src/Routes.php` wires them unconditionally: `ErrorMiddleware`,
`LogMiddleware`, `LivenessHandler`, `ReadinessHandler`, and `AuthenticationMiddleware` are in the skeleton body itself
(php-creating-skeleton, `references/routes.md`). A service missing a library its `src/Routes.php` wires does not boot.
That is the invariant, and it is stated about the wiring, never about who publishes the package. The auth row is the one
binding in the table: with `<auth-package>` unset there is no auth middleware to require, `src/Routes.php` wires the
route group without `AuthenticationMiddleware`, and declaring the package anyway is a finding because the install cannot
resolve it. Every other row holds in any organization.

A conditional library is added only when the service's code requires it:

| Concern              | Library                           | Add when                                                    |
|:---------------------|:----------------------------------|:------------------------------------------------------------|
| Value objects        | `tiny-blocks/value-object`        | The domain defines value objects.                           |
| Database abstraction | `doctrine/dbal`                   | The service persists state (a repository adapter exists).   |
| UUIDs                | `ramsey/uuid`                     | The domain generates UUID identifiers.                      |
| Time abstractions    | `tiny-blocks/time`                | The domain models time.                                     |
| Collections          | `tiny-blocks/collection`          | The domain uses typed collections.                          |
| Country codes        | `tiny-blocks/country`             | The domain models ISO-3166 country codes.                   |
| Money and currency   | `tiny-blocks/currency`            | The domain models monetary amounts.                         |
| Correlation id       | `tiny-blocks/http-correlation-id` | The service propagates a correlation id across calls.       |
| Query string parsing | `tiny-blocks/http-query`          | A read endpoint accepts filter, sort, or pagination params. |
| Object mapping       | `tiny-blocks/mapper`              | A read model or a payload is mapped from another shape.     |
| HTTP client          | `guzzlehttp/guzzle`               | The service calls an external HTTP API (a Gateway exists).  |
| Idempotency          | `<idempotency-package>`           | A write endpoint accepts an `Idempotency-Key`.              |
| Transactional outbox | `tiny-blocks/outbox`              | The service emits integration events.                       |

One row is capability-bound. With `<idempotency-package>` unset, a write endpoint that accepts an `Idempotency-Key`
still owes the guarantee and implements it inside the service, no package is added, and the trigger condition stays
exactly what it is. The condition describes what the code needs, the library column only names who supplies it.

The HTTP client row is conditional for the same reason every other row here is: the mandatory table above earns its
entries from `src/Routes.php` wiring them at boot, and nothing in the skeleton constructs a client. A service with no
outbound adapter never resolves one, so declaring it there ships an unused package and reads as a Gateway that does not
exist. `tiny-blocks/http` carries the outbound facade the adapters depend on and pulls no client of its own, so the
concrete client is declared exactly when a Gateway binds a transport to it (`php-hex-driven-http`, and the binding shape
in the php-creating-driven skill).

A package the service imports directly is declared directly, whatever else happens to pull it in. Reaching a class
through another package's dependency is an implicit coupling that breaks silently the day that package drops the row,
and the audit signal for it is one grep: every `use` prefix resolved in `src/` has a matching `require` entry.

Gateway-, provider-, and protocol-specific libraries (`stripe/stripe-php`, `aws/aws-sdk-php`) are not canonical: add
them per service when the matching driven adapter exists. Reuse of a tiny-blocks package goes through the
`php-reusing-tiny-blocks` skill before reaching outside the ecosystem. Versions are resolved against Packagist at sync
time and follow the dependency-policy cooldown in `CLAUDE.md` § Dependency policy, never declared in this rule.

### PHP extensions

An `ext-*` entry is declared when the service's own code (not a dependency's) calls that extension's functions directly.
`ext-pdo` accompanies `doctrine/dbal`, `ext-curl` accompanies `guzzlehttp/guzzle` when the service configures the cURL
handler itself, `ext-sodium` accompanies in-process encryption or signature verification, and `ext-openssl` accompanies
key or certificate handling. The `<base-images>` PHP base ships the official extension set plus `bcmath` and `pdo_mysql`
(docker-images rule), so declaring an extension documents the requirement, it never installs one. With `<base-images>`
unset the app `Dockerfile` installs whatever the upstream official image lacks, and the `composer.json` entry still only
documents the requirement. Either way a service that persists state and omits `ext-pdo` is a finding.

### Stability and private repositories

`minimum-stability` is `stable` with `prefer-stable` true. A service pinned to `dev` resolves development branches,
which defeats the dependency-policy cooldown in `CLAUDE.md` § Dependency policy, and is a finding.

Every private package declares its `repositories` entry. That is the portable invariant, and it is stated about the
package, never about a particular vendor. The block itself is present exactly when the service declares at least one
private package, and absent otherwise. Where `<auth-package>` is set it is mandatory and lives on a private VCS host, so
the block is part of the canonical body for that service, and every further private package the service uses
(`<idempotency-package>`, any other package under `<github-org>`) adds its own entry. With no private package declared
the file carries no `repositories` block at all, and an empty or vestigial one is a finding. The credential half of this
contract is § Private package authentication.

## Audit signal

The audit validates that every mandatory core library is present, that every conditional library appears only when its
trigger condition holds, that no canonical library lags a major behind the latest stable without an
`// @upstream Major <X>.0 available. Review before bumping.` comment, and that no service is pinned below the lowest
supported version of the matching library. A service running ahead of another on the same major is not a finding. A
major bump is adopted only by an explicit architectural decision, which removes the `@upstream` comment.

## Six scripts

`composer.json` exposes exactly six scripts: `configure`, `configure-and-update`, `fix-review`, `review`, `test-file`,
`tests`. The set is closed: a seventh public script is prohibited (new workflows live behind `tests` or `review`, or as
an internal script inside a container's own directory under `docker/`). The `Makefile` and CI reference these by name,
so renaming or removing any of them is prohibited. The composer scripts are the single source of truth for what each
command runs, and their bodies are in the php-creating-skeleton skill.

## Makefile shape

The public target set is closed: `start`, `stop`, `configure`, `configure-and-update`, `tests`, `test-file`, `review`,
`fix-review`, `show-reports`, `show-outdated`, `clean`, `help`. The README and the contributor workflow reference these
names, so renaming or removing any of them is prohibited, and a thirteenth public target is added only on an explicit
request. Each carries exactly one `## @<section>` tag, which is what places it in `make help`.

Those twelve are the whole file. No target sits outside the set, and none of them declares a prerequisite: whatever a
recipe needs, it does itself, inside its own body. Most preconditions need nothing done at all. A base image the daemon
does not hold is pulled by Docker when a runner names it or a `FROM` line reaches it (build versus pull is owned by
`docker-images` § Consuming), and an absent `.env.local` fails `docker compose` with an error naming the file, so a
target restating either buys nothing and costs a name in the file. The suite's Docker network is the one exception,
because no tool creates it on demand and its absence aborts the run that joins it. The `configure` recipe creates it,
silently and idempotently, guarded by an inspect so a second run is a no-op. It belongs there because `configure`
already precedes the suite on every path, a clone having no `vendor/` to run it with. Prose comments inside the file are
limited to the header and the section banners, because every rationale belongs in this rule instead.

The compose stack the `start` target brings up joins the shared external Docker network `<local-network>`, so the
services of neighboring stacks reach this one by container name. A network declared `external` is never created by
compose, and `docker compose up` aborts outright when it does not exist, so that network already existing is a
precondition of `make start` and not something the compose file repairs. With `<local-network>` unset the compose file
declares no external network at all, the stack uses its own project network, and it starts standalone. Either way this
is a different network from the suite's `$(PROJECT_NAME)-test_default`, which `APP_TEST_RUN` joins and the `configure`
recipe creates. Compose never creates an external network, so the stack's one stays a precondition, while the suite's is
the single one the file repairs.

Exactly two container runners exist, `APP_RUN` for single-shot tooling and `APP_TEST_RUN` for the suite. A third runner
is prohibited. Only `APP_TEST_RUN` mounts the Docker socket and joins the test network, because only the test bootstrap
starts sibling containers. Every variable the file declares is referenced by a recipe or another variable, and an
unreferenced one is removed rather than kept for symmetry.

Both runners execute as the invoking host user, so every artifact they produce (`vendor/`, `composer.lock`, the
autoloader, everything under `reports/`) stays owned by the developer and `clean` needs no privilege escalation. The two
runners must agree on the user. Running one as root and the other as the host user breaks `phpstan.neon`, whose `tmpDir`
sits under `reports/`, because whichever runner creates that directory locks the other one out.

`COMPOSER_HOME` points at a writable path inside the container, because the image home belongs to the image's own user
and an arbitrary uid cannot write there. The suite runner additionally joins the host's docker group when one exists,
which the test bootstrap needs to reach the Docker socket. The lookup yields nothing on a host without that group (macOS
with Docker Desktop), where the flag is omitted and the socket is reachable anyway.

A working copy created before this convention still carries root-owned artifacts, and the first `make configure` on it
fails with a permission error. Repairing it requires no host privilege, because a throwaway root container reaches the
same bind mount:

```
docker run --rm -u root -v "$PWD":/app -w /app --entrypoint sh <cli-image> \
  -c "chown -R $(id -u):$(id -g) vendor reports composer.lock .phpunit.cache"
```

The double quotes matter. Single quotes would defer the expansion to the container, where `id` reports root and the
command would set the very ownership it is meant to undo.

Terminal detection tests standard input (`[ -t 0 ]`), never standard output. Make captures the output of `$(shell ...)`
through a pipe, so `[ -t 1 ]` evaluates to false even on an interactive terminal and the detection degrades silently to
the non-interactive branch.

### Stack teardown

`stop` tears the stack down with `--volumes`, so the database volume leaves with the containers and the next `start`
begins on an empty schema that Flyway rebuilds from `database/migrations/`. That makes `stop` destructive, which its
`## @setup` line states outright rather than leaving the reader to discover it. The trade is deliberate and it holds
while the database carries nothing a developer authored by hand, which is the case for a proof of concept whose only
fixtures are the migrations themselves. It buys a stack that cannot drift: no volume survives a version bump of the
database image to be half upgraded on the next run, and no schema outlives the migration that created it. A service
that grows data worth keeping between runs drops the flag and gets the plain `down` back, a one-word change.

### Migration container removal

A service that owns a schema runs Flyway in a one-shot `<service-name>-migrate` compose service, and the `start` recipe
removes that container once it has done its job:

```
@docker compose --env-file .env.local rm -f $(PROJECT_NAME)-migrate
```

Compose offers no per-service auto-removal attribute. The `--rm` flag exists only on `docker compose run`, which is a
different execution path, so the removal is an explicit step. It sits after the `up` and never before, because the
application and the CDC depend on the migration through `service_completed_successfully`, a condition that requires the
container to exist in an exited state for the `up` to release them. Removing it during the `up` would let the
application start before the schema exists.

The removal is the last line of the recipe and carries no error tolerance. `.ONESHELL:` with
`.SHELLFLAGS := -eu -o pipefail -c` runs the whole recipe in a single shell under `set -e`, so a failed migration makes
the `up` exit non-zero and aborts the recipe before the removal line is reached. The container then survives with the
full Flyway log, reachable through `docker logs <service-name>-migrate`. A migration that passes leaves nothing behind,
a migration that fails leaves everything. Wrapping the removal in `|| true` destroys that guarantee, and moving it above
the `up` breaks the ordering.

A service that owns no schema has no migration container, and its `start` recipe carries no removal line. The
discriminator is local and needs no external catalog: a `database/migrations/` directory exists in the repository, or it
does not.

## Private package authentication

A service that declares a `repositories` entry in `composer.json` pointing at a private host cannot resolve that package
anonymously. Composer first tries the host's authenticated HTTPS API, and on a 404 falls back to cloning over the git
SSH transport. A base image that ships `git` but no `ssh` client (the `<base-images>` `cli` target is one) makes that
fallback die with `error: cannot run ssh: No such file or directory`, and the whole resolution aborts with exit code 1.

The invariant: every container runner in the `Makefile` that executes `composer` forwards the host credential. In the
canonical body that means both `APP_RUN` and `APP_TEST_RUN` carry `-e COMPOSER_AUTH`. The variable holds the JSON
document Composer expects (`{"<auth-type>": {"<host>": "<token>"}}`), is exported by the developer in a shell profile,
and is never committed. Forwarding it when it is unset is a no-op, so the flag stays in the canonical body regardless of
whether a given service has a private dependency today. The image-build half of the same story is owned by
`docker-images` (§ Secrets), which routes the identical value through a BuildKit secret.

This invariant is independent of `composer.lock`. A committed lock does not remove the need for the credential, because
the private package still has to be downloaded. Omitting the credential turns a fresh clone into a hard failure on the
first `composer install`, and a working copy that already carries a populated `vendor/` masks the defect until the next
clean installation.

## Coverage and mutation thresholds

`infection.json.dist` sets `minMsi: 100` and `minCoveredMsi: 100`. Lowering either is prohibited. The behavioral
discipline behind these thresholds (100% line and branch coverage, every mutant killed) is owned by `php-testing` (§
Coverage and mutation).

## reports consistency

Every test artifact path uses `reports/` (plural), consistent across the `composer tests` script, the
`infection.json.dist` logs, the `phpunit.xml` coverage and JUnit outputs, and the `Makefile` `show-reports` target.
`report/` (singular) is prohibited.

Artifacts group by producing tool, one subdirectory each, never loose at the root of `reports/`:

| Subdirectory         | Written by                        | Holds                                                                                                         |
|:---------------------|:----------------------------------|:--------------------------------------------------------------------------------------------------------------|
| `reports/coverage/`  | `phpunit.xml`, the `tests` script | `coverage-html/`, `coverage-xml/`, `coverage.txt`, `coverage-clover.xml`, `junit.xml`, `mutation-report.html` |
| `reports/infection/` | `infection.json.dist`             | `logs/` and the mutation `tmpDir`                                                                             |
| `reports/phpstan/`   | `phpstan.neon`                    | the analysis `tmpDir`                                                                                         |

The mutation HTML sits under `reports/coverage/` because `make show-reports` opens it next to the coverage HTML. A new
artifact goes into the subdirectory of the tool that writes it, and `make clean` removes `reports/` whole.
